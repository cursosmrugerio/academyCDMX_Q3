L	Es un patrón de diseño que invariablemente conduce a una mala solución a un

L	Blob: Este patrón suele representarse como una única librería (The blob) que
L	contiene la mayoría de la funcionalidad y que otras librerías utilizan
L	incorrectamente de apoyo.
L	Características:
L	- Compuesta de una sola clase con métodos execute
L	Complicada de reutilizar y probar.
L	- Puede ser costosa de cargar en memoria, usando recursos excesivos incluso
L	para operaciones imples.
L	- Una modificación "The Blob" causa que todas las librerías relacionadas deban
L	reinstalarse, creando un problema de indisponibilidad temporal del servicio y
L	una carga adicional al sistema.
L	Causas:
L	- Reparto de responsabilidades incorrecto: Es conveniente que se realice un

L	- Falta de cumplimiento de la Arquitectura: A veces este anti patrón crece
L	accidentalmente esto es resultado de una inadecuada revisión del diseño de
L	las librerías antes de su desarrollo
L	- Intervención demasiado limitada: En proyectos iterativos, los
L	desarrolladores tienden a agregar pequeñas piezas de funcionalidad a clases
L	existentes que ya están funcionando
L	Soluciones:
L	- La solución pasa por realizar un 'reafactoring" del rediseño entre las librerías
L	involucradas.
L	- La clave es mover comportamientos de "The Blob" a sus librerías
L	relacionadas, diferenciado por las entidades con las que trabajan, reduciendo

L	Unidad de despliegue
L	Una unidad de despliegue es una agrupación de componentes APХ (transacción, librería, dto) que
L	siguen el mismo ciclo de vida y se despliegan en bloque. Puede contener de uno a muchos
L	componentes APX. Cada aplicación puede tener las UD que quiera. Se puede tener una UD por
L	componente АPХ. Una UD se puede desplegar tanto en máquinas virtuales como contenedores con
L	el mismo código (siempre que los componentes puedan constituir un contenedor funcional).
L	La unidad de despliegue sirve para dar una solución de agrupación de componentes APХ en un mismo
L	repo. No es obligatorio juntar ninguno de nuestros componentes. De hecho, perfectamente podemos
L	tener una UD por cada una de nuestras transacciones, sin más componentes dentro.

L	Librerías multiruntime
L	Los recursos de tipo librería pueden ser utilizados indistintamente en APХ Online o АPХ Batch, por
L	este motivo, a partir del día 14/12/2022, se dará la posibilidad de desplegar estos recursos de forma
L	dual, es decir, en ambos runtimes simultáneamente. De esta manera, se facilita la operativa de
L	despliegue para estos casos y se garantiza la alineación de versiones entre Online y Batch.
L	Con esta nueva funcionalidad, es importante tener en cuenta algunas consideraciones:
L	• El tipo de runtime (Online, Batch o Dual) deberá ser seleccionado en el primer despliegue en
L	DEV que se realice de la librería, quedando establecido para los siguientes despliegues y sin
L	posibilidad de editar.
L	• Con el despliegue multiruntime no se permitirá desplegar versiones diferentes de una misma
L	librería en Online y Batch.
L	• Aunque el despliegue multiruntime implica intrínsecamente desplegar en dos runtimes
L	diferentes, a nivel de Consola y Techstack, computará como un único despliegue y cualquier
L	acción que se realice sobre el mismo: redeploy, rollback, etc,... aplicará, por tanto, en ambos
L	runtimes.
FILE	pdf00_p009_0.png	14
L	Regularización de librerías antiguas
L	Aquellas librerías que fueron desplegadas antes de estar operativa esta nueva funcionalidad, deberán
L	ser regularizadas por el developer cuando realice el siguiente despliegue en DEV seleccionando el
L	modo de despliegue requerido. Pueden darse varios casos:
L	• Si nuestra librería estaba desplegada en un único runtime (Online o Batch) y queremos que así
L	continúe, cuando se realice el siguiente despliegue en DEV, deberá seleccionarse la opción
L	Online o Batch según corresponda.
L	• Si nuestra librería estaba desplegada en un único runtime (Online o Batch) y queremos que a
L	partir de ahora se despliegue en modo multiruntime, cuando se realice el siguiente despliegue
L	en DEV, deberá seleccionarse la opción Dual (Online + Batch)
L	• Si nuestra librería tenía versiones desplegadas tanto en Online como en Batch, cuando se
L	realice el siguiente despliegue en DEV, deberá seleccionarse la opción Dual (Online + Batch).

L	Modelo de ramas
L	A partir del 10/08/2022 se implantará en APX un nuevo modelo de ramas unificado para
L	Arquitecturas que aplicará a cualquier tipo de recurso APX (UD, Librería, DTO, Shell Script y
L	Estáticos), quedando deprecados los actuales: modelo de APX y modelo para recursos de tipo Shell
L	Script y Estáticos. Este nuevo modelo, también basado en gitflow y con soporte a múltiples releases,
L	presenta algunos cambios respecto a los anteriores que es importante tener en cuenta:
L	• Se elimina la rama master pasando a ser develop la rama origen del código
L	• Para solucionar bugs sobre una rama release se usarán ramas bugfix (si la release que
L	queremos arreglar no está desplegada en Producción) o ramas hotfix (si la release que
L	queremos arreglar está desplegada en Producción)
L	• La creación de una rama release o el merge de un hotfix sobre la rama release desencadenará
L	automáticamente la creación de una release version en Consola Ether
L	• Para recursos de tipo Shell Script o Estáticos aplicará el mismo modelo que para el resto de
L	recursos y por tanto, será necesario trabajar con ramas release, bugfix y hotfix.
FILE	pdf00_p021_0.png	20
L	Los proyectos que ya estuvieran trabajando en sus repositorios con el modelo de ramas deprecado
L	no sufrirán gran impacto, sólo deberán tener en cuenta las siguientes consideraciones:
L	• La rama master quedará discontinuada, a efectos prácticos no genera ningún impacto, sólo
L	dejará de actualizarse con futuros cambios.
L	• La rama RC se mantiene deprecada y no tiene cabida en el nuevo modelo. Se recomienda que
L	las ramas RC a día de hoy abiertas y en desuso sean cerradas.
L	• Para recursos de tipo Shell Script y Estáticos:
L	• No se podrán integrar nuevos cambios en la rama master ni realizar despliegues desde
L	ésta.
L	• Para desplegar cualquier cambio en Producción, será necesario abrir una rama release
L	desde develop desplegar desde ésta.

L	La automatización del modelo

L	Nombrado de las versiones
L	El versionado semántico que se establece dentro del modelo de ramas de APX es 'X.Y.Z", añadiendo el
L	sufijo '-[SNAPSHOT]' si se trata de una versión provisional.
L	• Major version X (X.y.z | X > O) Se incrementará cuando se produzcan cambios incompatibles
L	con la versión anterior. Patch y minor son reiniciadas a O cuando una versión mayor es
L	incrementada. Ejemplo: 2.0.0
L	• Minor version Y (x.Y.z | Y > O) Se incrementará cuando se introduzca funcionalidad nueva y
L	compatible con la versión anterior, puede incluir cambios a nivel de parches. Patch es
L	reiniciada a 0 cuando una versión menor se incrementa. Ejemplo: 1.3.0
L	• Patch version Z (x.y.Z | Z > O) Se incrementará cuando se introduzcan correcciones de errores
L	(un cambio interno que corrige un comportamiento incorrecto). Ejemplo: 1.3.1

L	Testing en APX
L	Como ya se ha comentado, una de las tareas que realiza nuestro pipeline en el proceso de
L	construcción de un recurso es la ejecución de Test Unitarios. Si en la ejecución alguno de los tests
L	fallara, el pipeline terminaría con error en este punto. Si desea consultar información sobre cómo
L	implementar tests unitarios en APX puede consultar en Platform los siguientes enlaces: Lesting in
L	АРХ Online , Testing Codelab, Testing in АРХ Batch.
L	La norma establecida en APX en cuanto a Test Unitarios es tener una cobertura de al menos el 80%
L	sobre el nuevo código. Esto lo valida también el pipeline a través de Sonar, en caso de no llegar a la
L	cobertura exigida, el pipeline terminará con error. (Puede consultar en detalle el Quality Gate
L	definido para APX así como las reglas Sonar aplicadas en APX en los siguientes enlaces: Quality Gate,
L	reglas Sonar APX).
L	Para la ejecución de pruebas integradas, la Arquitectura ofrece un Entorno Local APX para el
